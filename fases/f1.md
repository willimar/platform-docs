# Estudo da F1 — Anatomia da execução que você acabou de rodar

Excelente momento pra estudar: o log do seu terminal é um **trace completo** do sistema. Vou usar ele como guia, mapeando cada linha de log ao módulo que a gerou. Assim você entende não só o que cada peça faz, mas **quando e por que** ela entra em cena.

---

## 1. Mapa dos módulos (quem é quem)

| Módulo | Responsabilidade | Eventos de log que ele gera |
|---|---|---|
| `config/loader.py` | Lê e valida o YAML | `carregando_agente`, `agente_carregado` |
| `config/schema.py` | Modelos Pydantic (regras do YAML) | *(silencioso — valida)* |
| `tools/registry.py` | Descobre e executa ferramentas | `carregando_modulo`, `executando_ferramenta` |
| `engine/executor.py` | **O loop principal** | `iniciando_execucao`, `passo_iniciado`, `resposta_llm_invalida`, `agente_finalizado`, `execucao_concluida` |
| `llm/ollama.py` | Fala HTTP com o Ollama | `chamando_ollama`, `ollama_resposta_recebida` |
| `llm/parser.py` | Interpreta o JSON do LLM | `json_invalido`, `resposta_final`, `resposta_tool_call` |
| `engine/state.py` | Estado explícito da execução | *(silencioso — é dado, não ação)* |
| `cli.py` | Cola tudo e mostra na tela | *(prints coloridos, não logs)* |

## 2. A execução, fase a fase

### Fase A — Carga (loader + schema)

```
{"event": "carregando_agente", "caminho": "...agent.yaml"}     ← loader.py abre o arquivo
{"event": "agente_carregado", "nome": "Echo Agent", ...}      ← Pydantic validou, AgentConfig pronto
[OK] Agente carregado: Echo Agent v1.0.0                       ← cli.py
```

O `loader.py` lê o YAML e entrega o dict pro `schema.py`. O Pydantic checa tudo: versão é SemVer? ferramentas não vazias? temperatura entre 0 e 2? Se algo falhar, `AgentLoadError` e o programa para **antes** de gastar chamada de LLM. Validação cedo = erro barato.

### Fase B — Descoberta de ferramentas (registry + agent-sdk)

```
{"event": "carregando_modulo", "modulo": "mock_tools"}         ← registry.py importa o arquivo
[OK] 2 ferramenta(s) carregada(s)                              ← cli.py
```

Aqui acontece a mágica do decorator. Quando o `registry.py` importa `mock_tools.py` via `importlib`, o Python **executa o módulo** — e executar o módulo significa executar os decorators `@tool(...)`, que registram as funções no registry global do `agent-sdk`. Depois o `ToolRegistry` local copia essas specs pra si.

> **Por que um registry local por execução?** Se dois agentes rodarem em sequência, um não deve herdar as ferramentas do outro por acidente. O registry global do SDK é só o "ponto de encontro"; cada execução monta seu próprio conjunto.

### Fase C — O loop, passo 1 (executor + ollama + parser)

```
{"event": "iniciando_execucao", "max_passos": 3}               ← executor monta o AgentState
{"event": "passo_iniciado", "passo": 1}
{"event": "chamando_ollama", "num_mensagens": 2}               ← system + user
{"event": "ollama_resposta_recebida", "tamanho": 215}
{"event": "json_invalido", "erro": "Extra data: line 2 column 1 (char 128)"}   ← parser.py
{"event": "resposta_llm_invalida", "passo": 1}                 ← executor trata o erro
```

Olha o que o LLM fez: ele tentou chamar **duas ferramentas de uma vez**, devolvendo dois objetos JSON colados:

```json
{"acao": "usar_ferramenta", "ferramenta": "echo_repetir", ...}
{"acao": "usar_ferramenta", "ferramenta": "math_somar", ...}
```

Isso não é um JSON válido (é "JSON lines"). O `parser.py` falhou com `Extra data` e lançou `LLMParseError`.

Agora repare na decisão de design mais importante do executor: **ele não quebra**. Ele captura o erro, anexa uma mensagem de correção ao histórico ("sua resposta não está no formato correto, tente de novo") e volta pro topo do loop. O LLM vê o próprio erro e se corrige. Isso é o que separa um protótipo de uma plataforma.

### Fase D — O loop, passo 2

```
{"event": "passo_iniciado", "passo": 2}
{"event": "chamando_ollama", "num_mensagens": 4}   ← system, user, assistant(errado), user(correção)
{"event": "ollama_resposta_recebida", "tamanho": 107}
{"event": "resposta_final", "tamanho": 72}         ← parser entendeu: acao=finalizar
{"event": "agente_finalizado", "passo": 2}
{"event": "execucao_concluida", "status": "finalizado"}
```

Note o `num_mensagens: 4`. O histórico cresceu: o LLM recebe **toda a conversa**, incluindo o erro anterior. É assim que ele "aprende" dentro da execução — não há treinamento, só contexto. O executor então seta `state.resultado`, `status = FINALIZADO` e sai do loop com `break`.

### Fase E — Apresentação (cli)

O `cli.py` lê o `AgentState` final e imprime o painel verde + as estatísticas. A CLI não sabe nada do loop; ela só **renderiza o estado**.

## 3. Duas lições de ouro que essa execução te deu

### Lição 1 — O caminho defensivo foi exercitado de verdade

O contrato "responda sempre em JSON" foi violado pelo LLM na primeira tentativa, e o sistema sobreviveu. Quando você projetar sistemas com LLM, **assuma que o LLM vai violar o contrato** às vezes. Todo o design do parser + executor parte dessa premissa.

### Lição 2 — O modelo "colou" (e isso é um problema real)

Olhe a última linha do seu print:

```
Passos: 2 | Ferramentas usadas: 0 | Duração: 15.83s
```

**Ferramentas usadas: 0.** O LLM nunca chamou `echo_repetir` nem `math_somar`. Ele respondeu `{'repetido': ..., 'resultado': 5}` direto — ele *sabia* que 2+3=5 e simulou o eco. O resultado parece certo, mas as ferramentas foram ignoradas.

No echo-agent isso é inofensivo. Num agente de agenda seria **catastrófico**: o modelo inventaria eventos em vez de consultar a API. Isso tem nome: *tool-use non-compliance*, e é mais comum em modelos menores (8B).

Mitigações que você vai estudar nas próximas fases:

| Mitigação | Onde entraria |
|---|---|
| Reforçar no system prompt: "Você DEVE usar ferramentas, nunca adivinhe resultados" | `executor.montar_system_prompt` |
| Validar a saída contra `saida_esperada` antes de aceitar `finalizar` | novo passo no executor |
| Exigir ≥1 tool call pra tarefas que marcam `requer_ferramentas: true` no YAML | `schema.py` + executor |
| Usar modelo maior pra tarefas críticas | `modelo` no YAML |

Guarde essa observação — ela vale um ADR no futuro.

## 4. Por que construí assim (decisões de design)

- **`AgentState` explícito (dataclass)** — herdado do LangGraph. Tudo que acontece é dado inspecionável: você pode logar, serializar, debugar. Sem estado escondido.
- **Parser separado do executor** — testável sem LLM. Seus 9 testes de parser rodam em milissegundos, sem rede.
- **`LLMClient` como interface abstrata** — o executor não sabe que existe Ollama. Amanhã você cria `OpenAIClient(LLMClient)` e troca sem tocar no loop.
- **YAML → prompt via template** — quem escreve agente não faz prompt engineering; o template garante consistência do contrato JSON.
- **`while` com `max_passos`** — proteção contra loop infinito. LLM confuso + ferramenta quebrada não pode custar dinheiro pra sempre.
- **Retry com correção em vez de exceção** — erro de formato é recuperável; o próprio LLM é quem conserta.

## 5. Ordem de leitura recomendada do código

Pra estudar com calma, leia nesta ordem (cada arquivo só depende dos anteriores):

```
1. agent-sdk/src/agent_sdk/types.py        ← o vocabulário (ToolResult, ToolSpec)
2. agent-sdk/src/agent_sdk/decorators.py   ← como ferramentas nascem
3. platform-core/.../engine/state.py       ← o estado que circula
4. platform-core/.../llm/parser.py         ← o contrato JSON
5. platform-core/.../tools/registry.py     ← descoberta + execução segura
6. platform-core/.../config/schema.py      ← as regras do YAML
7. platform-core/.../config/loader.py      ← carga validada
8. platform-core/.../llm/ollama.py         ← HTTP + tratamento de erro de rede
9. platform-core/.../engine/executor.py    ← o loop (leia por último, é a síntese)
10. platform-core/.../cli.py               ← o ponto de entrada
```

## 6. Exercícios pra fixar (30 min)

1. **Caminho do timeout:** mude `max_passos: 1` no `agent.yaml` e rode. Você vai ver `limite_passos_atingido` e o painel vermelho de `TIMEOUT`.
2. **Caminho do erro de ferramenta:** faça `math_somar` lançar `ToolExecutionError("API caiu", retry=True)` e observe os logs de retry no registry.
3. **Faça o modelo usar ferramentas de verdade:** reforce as instruções no YAML ("NUNCA calcule por conta própria, sempre chame math_somar") e rode até ver `Ferramentas usadas: 2` e o log `executando_ferramenta`.
4. **Desenhe o diagrama de sequência** a partir dos logs (quem chama quem, em que ordem). Comparar com o diagrama do `architecture.md` é o melhor teste de que você entendeu.
