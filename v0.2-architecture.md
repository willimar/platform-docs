# v0.2-architecture.md — Arquitetura da Agent Platform v0.2

# Agent Platform v0.2 — Arquitetura

> **Visão**: reescrita do motor em .NET 10 com arquitetura hexagonal,
> microserviços isolados (local-first via Docker Compose), persistência
> em MongoDB Atlas (config) + Redis (sessões conversacionais).
> AWS só entra na v0.3.

---

## 1. Princípios de design

| Princípio | Como se aplica |
|---|---|
| **Cloud-agnostic** | v0.2 roda 100% local via Docker Compose; AWS é adapter na v0.3 |
| **Hexagonal** | Domínio puro (Core) depende de ports; adapters implementam |
| **Isolamento por agente** | Cada agente = worker container independente |
| **Contratos via NuGet** | `AgentPlatform.Contracts` é a fonte de verdade tipada |
| **Dados diferentes → stores diferentes** | Mongo (config durável) + Redis (sessões efêmeras com TTL) |

        double temperature,
        TimeSpan timeout,
        CancellationToken ct);

{
    Task<ToolSpec?> ResolveAsync(string name);

// IConfigLoader — carrega e valida o YAML do agente
public interface IConfigLoader
{
    Task<AgentSpec> LoadAsync(string yamlPath);

## 4. Serviços detalhados

### 4.1 YARP Gateway (port 5000)

**Responsabilidade**: roteamento, JWT validation, rate limiting, health checks.

**Endpoints**:
- `/api/agents/{name}/execute` → Executor Service
- `/api/agents/{name}/validate` → Registry Service
- `/api/agents/{name}/tools` → Registry Service
- `/api/chat` → Executor Service (sessões conversacionais)
- `/api/system/health` → todos os serviços

**Configuração YARP**:

```json
{
  "ReverseProxy": {
    "Routes": {
      "executor-route": {
        "ClusterId": "executor-cluster",
        "Match": { "Path": "/api/execute/{**catch-all}" }
      },
      "chat-route": {
        "ClusterId": "executor-cluster",
        "Match": { "Path": "/api/chat/{**catch-all}" }
      },
      "registry-route": {
        "ClusterId": "registry-cluster",
        "Match": { "Path": "/api/agents/{**catch-all}" }
      }
    },
    "Clusters": {
      "executor-cluster": {
        "Destinations": {
          "executor": { "Address": "http://executor:8080" }
        }
      },
      "registry-cluster": {
        "Destinations": {
          "registry": { "Address": "http://registry:8080" }
        }
      }
    }
  }
}
```

### 4.2 Agent Registry Service (port 5002)

**Responsabilidade**: CRUD de agentes, valida YAML spec, armazena config no MongoDB.

**Stack**: ASP.NET Core + MongoDB.Driver + YamlDotNet

**Endpoints**:
- `POST /agents` → valida YAML + registra no Mongo
- `GET /agents/{name}` → retorna spec
- `GET /agents` → lista todos
- `DELETE /agents/{name}`
- `POST /agents/{name}/tools` → upload de tool package (.nupkg)

**Formato do documento Mongo**:

```json
{
  "_id": "youtube-publisher-agent",
  "nome": "YouTube Publisher Agent",
  "versao": "0.1.0",
  "specYaml": "<yaml cru, pra auditoria/re-parse>",
  "spec": {
    "modelo": "llama3.1:8b",
    "maxPassos": 5,
    "ferramentas": ["youtube_list_channels", "..."]
  },
  "tags": ["youtube", "publicacao"],
  "status": "ativo",
  "criadoEm": "2026-08-19T00:00:00Z",
  "atualizadoEm": "2026-08-19T00:00:00Z"
}
```

### 4.3 Agent Executor Service (port 5001)

**Responsabilidade**: recebe request de execução, invoca o Worker do agente via Docker, retorna resultado.

**Stack**: ASP.NET Core + Docker client (Docker.DotNet)

**Endpoints**:
- `POST /execute/{agentName}` → invoca worker container, aguarda, retorna
- `POST /chat` → sessão conversacional (carrega sessão do Redis, invoca worker, persiste)

**Fluxo de execução (one-shot)**:

```
1. Client → POST /api/execute/youtube-publisher-agent
2. Executor → docker run youtube-publisher-worker (invoca container)
3. Worker:
   - Lê agent.yaml do volume montado
   - Carrega tools do volume
   - Executa loop com Ollama (chama localhost:11434)
   - Retorna ToolResult via stdout (JSON)
4. Executor → retorna pro client
```

**Fluxo conversacional**:

```
1. Client → POST /api/chat { sessionId?, mensagem }
2. Executor:
   - Se sessionId vazio → cria nova sessão (id = GUID)
   - Carrega sessão do Redis
   - Invoca worker com sessão + mensagem
3. Worker:
   - Executa 1 turno do loop
   - Retorna resposta + estado atualizado
4. Executor:
   - Persiste sessão no Redis (TTL renovado)
   - Retorna resposta + sessionId pro client
```

### 4.4 Agent Workers (containers isolados)

**Responsabilidade**: executa o loop reason→act→observe para UM agente específico.

**Stack**: .NET 10 console app + AgentPlatform.Core + AgentPlatform.Adapters

**Isolamento total**: cada Worker tem seu próprio:
- Tool registry (só as tools dele)
- OAuth credentials (secrets do agente via volume)
- Dependências (Google APIs, etc.)

**Comunicação**: stdin/stdout (JSON) ou HTTP endpoint interno

**Dockerfile.worker**:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY src/AgentPlatform.Contracts ./AgentPlatform.Contracts
COPY src/AgentPlatform.Core ./AgentPlatform.Core
COPY src/AgentPlatform.Adapters ./AgentPlatform.Adapters
COPY src/Workers/${AGENT_NAME}Worker ./Worker
RUN dotnet publish ./Worker -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "Worker.dll"]
```

## 7. Sessões conversacionais

### 7.1 Conceitos

| Conceito | O que é |
|---|---|
| **Sessão** | id + histórico + estado + metadados (criada em, último acesso) |
| **Turno** | 1 mensagem do usuário → 1 resposta do agente (com N tool calls internos) |
| **Estado da sessão** | fatos estruturados: usuário identificado, ticket aberto, escopo |

### 7.2 Formato do `SessionRecord`

```csharp
public sealed class SessionRecord
{
    public string Id { get; set; } = Guid.NewGuid().ToString("N");
    public string AgentName { get; set; } = string.Empty;
    public List<ChatMessage> History { get; set; } = new();
    public Dictionary<string, object?> State { get; set; } = new();
    public DateTime CreatedAt { get; set; } = DateTime.UtcNow;
    public DateTime LastAccess { get; set; } = DateTime.UtcNow;
}
```

### 7.3 RedisSessionStore (TTL nativo)

```csharp
public sealed class RedisSessionStore : ISessionStore
{
    private readonly IDatabase _db;
    private readonly TimeSpan _ttl;

    public RedisSessionStore(IConnectionMultiplexer redis, TimeSpan ttl)
    {
        _db = redis.GetDatabase();
        _ttl = ttl;
    }

    private static string Key(string id) => $"session:{id}";

    public async Task<SessionRecord?> LoadAsync(string id, CancellationToken ct = default)
    {
        var json = await _db.StringGetAsync(Key(id));
        return json.IsNullOrEmpty
            ? null
            : JsonSerializer.Deserialize<SessionRecord>(json!);
    }

    // Cada save renova o TTL → "sliding expiration"
    public Task SaveAsync(SessionRecord session, CancellationToken ct = default)
        => _db.StringSetAsync(Key(session.Id),
             JsonSerializer.Serialize(session), _ttl);

    public Task DeleteAsync(string id, CancellationToken ct = default)
        => _db.KeyDeleteAsync(Key(id));
}
```

### 7.4 Evolução do YAML para conversa

```yaml
nome: "Suporte Tecnico Agent"
versao: "0.1.0"
modelo: "llama3.1:8b"
instrucoes: >
  Voce e um agente de suporte tecnico.
  Primeiro identifique o usuario (email ou numero de ticket).
  Guarde a identificacao com sessao_salvar.
  NUNCA pergunte de novo o que ja esta no estado da sessao.
ferramentas:
  - identificar_usuario
  - listar_chamados
  - abrir_chamado
conversa:                      # nova seção opcional
  ttl_minutos: 30
  max_turnos: 50
  passos_por_turno: 5          # o atual max_passos, mas POR TURNO
```

**Regra de schema**: ou `tarefa` (one-shot, v0.1) ou `conversa` (stateful, v0.2).

### 7.5 Tools built-in de sessão

Quando `conversa:` existe, o registry ganha automaticamente:

- `sessao_salvar(chave, valor)` — o LLM guarda "usuario=ana@acme.com"
- `sessao_ler(chave)` — relê sem perguntar de novo

E o system prompt de cada turno inclui `Estado da sessao: {...}`.

## 10. Decisões arquiteturais

| Decisão | Escolha | Alternativa considerada | Por quê |
|---|---|---|---|
| Linguagem | .NET 10 | Python (v0.1) | Tipagem estática, deploy single-file, ecossistema enterprise |
| Arquitetura | Hexagonal | Monolito / MVC | Isolamento de domínio, testabilidade, adapters trocáveis |
| Persistência de config | MongoDB Atlas | SQLite / PostgreSQL | Documentos flexíveis, free tier, sem vendor lock-in |
| Sessões conversacionais | Redis (TTL nativo) | Mongo TTL index / arquivo | Latência <1ms, expiração automática, zero código de limpeza |
| Orquestração local | Docker Compose | Kubernetes / Nomad | Simplicidade, local-first, sem overhead |
| Gateway | YARP.ReverseProxy | Nginx / Traefik | Integração nativa ASP.NET Core, config em JSON |
| Isolamento de agentes | Worker container por agente | Thread pool compartilhado | Falha de um não afeta os outros, deploy independente |
| Comunicação Executor→Worker | Docker exec (stdin/stdout) | gRPC / HTTP | Simplicidade pra v0.2; gRPC na v0.3 se precisar de streaming |

## 11. Contraste com v0.1 (Python)

| Aspecto | v0.1 (Python CLI) | v0.2 (.NET microserviços) |
|---|---|---|
| Deploy | Local (uv run) | Docker Compose (6 serviços) |
| Isolamento | Processo por run | Container por agente |
| Estado | Nenhum | Mongo (config) + Redis (sessões) |
| Escala | Single machine | Múltiplos containers |
| Observabilidade | Logs JSON local | Serilog + Docker logs |
| Custo | Grátis (local) | Grátis (local), pago na v0.3 (AWS) |
| Linguagem | Python 3.12 | .NET 10 (C#) |
| Conversação | Não suportada | Sessões com TTL (Redis) |
