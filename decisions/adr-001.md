## 1. Contexto

A plataforma precisa de um modelo genérico para definição e execução
de agentes. Requisitos:

- Qualquer pessoa deve conseguir **plugar um agente novo** sem alterar
  o código da plataforma.
- A definição de um agente deve ser **declarativa** (arquivo de
  configuração, não código).
- O motor de execução deve ser **explícito e debugável** (sem "magia"
  escondida).
- O modelo deve funcionar com **LLMs locais** (Ollama) e remotos.
- A curva de entrada pra criar o primeiro agente deve ser **minutos,
  não dias**.

Não queremos reinventar um framework completo. Queremos extrair os
padrões que funcionam e descartar o excesso.

---

## 2. Alternativas avaliadas

### 2.1 CrewAI

| Aspecto                  | Avaliação |
|--------------------------|-----------|
| Definição declarativa    | ✅ YAML nativo, muito legível |
| Separação agente/tarefa  | ✅ `role`, `goal`, `expected_output` |
| Ferramentas via decorator| ✅ Simples e eficaz |
| Orquestração embutida    | ⚠️ Conveniente, mas esconde a lógica |
| Metáfora "role-playing"  | ❌ Overkill, adiciona complexidade sem valor real |
| Processos hierárquicos   | ❌ Escopo desnecessário neste momento |
| Estado interno           | ❌ Implícito, difícil de debugar |

### 2.2 LangGraph

| Aspecto                  | Avaliação |
|--------------------------|-----------|
| Estado explícito         | ✅ TypedDict, controle total |
| Loop com condição de saída| ✅ `usar_ferramenta` vs `finalizar` |
| Separação raciocínio/execução | ✅ Nós distintos |
| Flexibilidade do grafo   | ✅ Poderoso pra casos complexos |
| Abstrações               | ❌ StateGraph, CompiledGraph, MessageGraph… excesso |
| Curva de aprendizado     | ❌ Alta pra quem está começando |
| Definição declarativa    | ❌ Tudo em código, sem YAML |
| Checkpoints / persistência| ⚠️ Útil, mas não é prioridade agora |

---

## 3. Decisão

**Adotar um modelo próprio composto**, extraindo:

- Do **CrewAI**: a camada declarativa (YAML), a estrutura de tarefa
  com `descricao` / `saida_esperada`, e o padrão de ferramentas
  via decorator com docstring.
- Do **LangGraph**: o estado explícito, o loop condicional de
  execução, e a separação entre raciocínio e execução de ferramentas.

**Descartar** tudo que não serve ao escopo atual (seção 5).

---

## 4. O que adotamos

### 4.1 Do CrewAI

| Elemento | Como usamos |
|----------|-------------|
| Definição em YAML | Formato canônico de declaração de um agente |
| Campos `role` / `goal` | Renomeados para `nome` / `instrucoes`. Alimentam o system prompt |
| `description` + `expected_output` na tarefa | Mantidos como `tarefa.descricao` e `tarefa.saida_esperada` |
| Decorator `@tool` + docstring | Padrão de registro de ferramentas. A docstring é a descrição que o LLM vê |
| `max_iter` | Adotado como `max_passos` pra evitar loops infinitos |

### 4.2 Do LangGraph

| Elemento | Como usamos |
|----------|-------------|
| Estado explícito | Objeto `AgentState` tipado que circula pelo loop |
| Loop condicional | A cada passo: LLM decide entre `usar_ferramenta` ou `finalizar` |
| Separação de responsabilidades | Motor de raciocínio ≠ executor de ferramentas |
| Fluxo: entrada → raciocínio → ferramenta → raciocínio → … → fim | Padrão do loop de execução |

---

## 5. O que descartamos

| Elemento | Origem | Motivo |
|----------|--------|--------|
| `backstory` | CrewAI | Prompt engineering disfarçado. Um campo `instrucoes` livre resolve |
| `Process.hierarchical` | CrewAI | Multi-agente com "gerente" é escopo futuro, não atual |
| Agentes conversando entre si | CrewAI | Overkill. Nossa plataforma executa tarefas, não simula reuniões |
| `StateGraph` / `CompiledGraph` | LangGraph | Abstrações pesadas demais. Um loop `while` bem feito resolve |
| `MessageGraph` | LangGraph | Não precisamos de grafo de mensagens no MVP |
| Checkpoints / persistência de estado | LangGraph | Feature de v2.0. Agora o estado vive em memória |
| `ToolNode` como classe separada | LangGraph | Nossa tool registry resolve com menos camadas |
| Sistema de `Human-in-the-loop` embutido | LangGraph | Pode ser adicionado depois como uma "ferramenta" especial |

## 6. Modelo resultante

### 6.1 Esquema de definição de agente (YAML)

```yaml
# agent.yaml
nome: "Ler Agenda Google"
versao: "1.0.0"
modelo: "llama3.1:8b"
instrucoes: >
  Você é um assistente que consulta a agenda do usuário.
  Responda sempre em português, de forma concisa.
ferramentas:
  - google_calendar_list_events
max_passos: 5

tarefa:
  descricao: >
    Consulte os próximos eventos da agenda do usuário.
  saida_esperada: >
    Lista formatada com data, hora e título de cada evento,
    ordenada cronologicamente.
```

### 6.2 Esquema do estado de execução

```python
@dataclass
class AgentState:
    """Estado que circula pelo loop de execução."""
    mensagens: list[dict]       # histórico da conversa com o LLM
    passo_atual: int = 0        # contador de iterações
    resultado: str | None = None # saída final do agente
    erro: str | None = None     # mensagem de erro, se houver
    status: str = "em_execucao" # em_execucao | finalizado | erro
```

### 6.3 Loop de execução (pseudocódigo)

```python
def executar_agente(config: AgentConfig, tools: ToolRegistry) -> AgentState:
    state = AgentState(mensagens=[montar_system_prompt(config)])

    while state.passo_atual < config.max_passos:
        # 1. RACIOCÍNIO — pergunta ao LLM o que fazer
        resposta = llm.invoke(state.mensagens)

        # 2. DECISÃO — o LLM quer usar ferramenta ou finalizar?
        if resposta.pede_ferramenta():
            # 3. EXECUÇÃO — chama a ferramenta no registry
            resultado = tools.executar(
                nome=resposta.ferramenta,
                parametros=resposta.parametros,
            )
            state.mensagens.append({"role": "tool", "content": resultado})
        else:
            # 4. FINALIZAÇÃO
            state.resultado = resposta.texto
            state.status = "finalizado"
            break

        state.passo_atual += 1

    if state.status == "em_execucao":
        state.status = "erro"
        state.erro = "Limite de passos atingido sem conclusão."

    return state
```

### 6.4 Registro de ferramentas (decorator)

```python
TOOL_REGISTRY: dict[str, Callable] = {}

def tool(nome: str):
    """Decorator que registra uma função como ferramenta disponível."""
    def decorator(fn):
        TOOL_REGISTRY[nome] = {
            "funcao": fn,
            "descricao": fn.__doc__,
            "parametros": inspecionar_assinatura(fn),
        }
        return fn
    return decorator
```

### 6.5 Formato de resposta esperado do LLM

O LLM deve responder sempre em JSON:

```json
// Quando quer usar uma ferramenta:
{
  "acao": "usar_ferramenta",
  "ferramenta": "google_calendar_list_events",
  "parametros": { "qtd": 5 }
}

// Quando quer finalizar:
{
  "acao": "finalizar",
  "resposta": "Aqui estão seus próximos eventos..."
}
```

### 8. Consequências
Positivas

* Baixa barreira de entrada. Criar um agente = escrever um YAML
  - implementar as ferramentas. Não precisa conhecer o motor.
* Debugável. O estado é explícito. Cada passo gera log. Dá pra rastrear exatamente o que o LLM decidiu e por quê.
* Testável. O loop pode ser testado com ferramentas mock e LLM fake, sem depender de APIs externas.
* Extensível. Adicionar uma ferramenta nova = decorar uma função. Adicionar um agente novo = criar um YAML + tools.

#### Negativas / riscos aceitos

* Menos flexível que LangGraph. Não temos grafo, ramificação     condicional complexa, nem paralelismo. Se um agente precisar disso no futuro, teremos que evoluir o motor.
* Dependemos da capacidade do LLM de gerar JSON válido. Modelos pequenos podem errar o formato. Precisamos de retry e fallback no parser.
* Sem persistência de estado. Se o processo morrer no meio, perde tudo. Aceitável pro MVP. Na v2, adicionar checkpoints.

#### Dívidas técnicas conscientes

* Suporte a múltiplos modelos num mesmo agente (ex: modelo barato pra triagem, modelo caro pra execução)
* Execução paralela de ferramentas independentes
* Aprovação humana como passo do loop (human-in-the-loop)
* Persistência / retomada de execução
